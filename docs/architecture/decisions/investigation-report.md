# ADR: Change Investigation Report

**Decision:** The developer-facing workflow is one function, `investigateChange` (`src/investigation/`), and one command, `tracebound-investigate` (`src/cli/investigate.ts`, `npm run investigate`). It composes the existing pipeline without changing it: `searchHybridDetailed`, then `constructEvidence` on that same run, then, only when a reasoning provider is supplied, `assessImpact` on that same evidence package. The result is an `InvestigationReport` (JSON) with a Markdown rendering.
**Context:** M8 often abstains, and under instructions 1.2.0 it may answer `insufficient_evidence` for every candidate. Tracebound must still help a developer decide what to look at. The evidence package already says why each file was retrieved, so the report is built around that package, with the assessment as an optional layer.
**Chosen approach:**
- **One run, exact provenance.** Every candidate carries the M7 evidence objects exactly as `constructEvidence` built them (ids included), its retrieval signals from the same fused ranking, and one line in words per evidence item with the same id. Nothing is retrieved, embedded or built twice, and nothing is stored.
- **Limitations and open questions are derived, not generated.** Fixed rules read the evidence: no structural relationship, a relationship only from the changed file to the candidate (a dependency, not a dependent), an import declaration that was not located, path-only term matches, a missing or truncated excerpt, a candidate found by only one ranking. Each report also states that signals are not proof of impact, which changed paths are absent from the snapshot (with the file-policy exclusion when one was recorded), and how many ranked files were not described.
- **The assessment is shown only when accepted.** `reasoning.status` is `not_requested`, `accepted`, `rejected` (the validator refused an answer) or `failed` (provider error, timeout, input too large). Only `accepted` attaches classifications and findings; a rejection or failure is reported, the evidence is still shown, and the command still exits 0. `insufficient_evidence` is described as "not a finding that the file is unaffected".
- **Missing prerequisites fail explicitly.** An unknown or failed snapshot, a missing index or evidence that cannot be verified against the snapshot raises the existing typed error; the command prints it and exits 1. The command builds missing indexes for a snapshot it is given (the semantic index embeds the snapshot) and says so on standard error. Both Ollama providers, and so a named reasoning model, are checked before anything is ingested or indexed.
- **Git-native change input** (`src/investigation/change-set.ts`, `diffCommits` and `isAncestor` in `src/git/git.ts`): `--repo --base --head` derives the change from two commits. Both must be full commit SHAs of commits in the repository; refs are never resolved and the working tree, index and HEAD are never read. The base must differ from the head and be its ancestor (`git merge-base --is-ancestor`); diverged or reversed ranges are refused rather than compared through a merge base, so the report always describes "the head's changes on top of the base". The changes come from `git diff-tree -r -z -M --name-status` (argument array, no shell): added, modified, deleted, renamed (with Git's similarity) and type-changed files; copies are not detected. The changed paths passed to `investigateChange` are every changed path, with a rename's old path (present in the base) before its new path (absent). The change is investigated in the **base snapshot**, the state before the change, which is the state the candidates must be judged in. The range is validated and diffed before anything is ingested; an empty diff is an error. The range is recorded in the report (`commitRange`), each changed file carries how it changed, and `investigateChange` refuses a range whose base is not the snapshot's commit or whose derived paths differ from the changed paths it was given.
- **Command dependencies are injectable** (embedding and reasoning providers, output), so the command is tested end to end with fake providers.
- **Both renderings from one run.** `--json-out <file>` writes the JSON report next to the `--format` output, so the Markdown and the JSON describe the same retrieval instead of two runs that each embed the description. Report paths are checked (distinct files, existing directories) before the database is opened, because building a semantic index can take minutes; so is the directory of `--db`. Commit-id and embedding-provider errors add a `hint:` line naming the fix; the hints live in the command, not in the shared Git and Ollama modules.
**Not changed:** retrieval, evidence, the M8.1 validator and grounding guards, the reasoning instructions and the output schema.
**Deferred:** using the diff content itself (hunks, changed symbols) rather than only the changed paths; deriving the description from commit messages (it is still required); ranges whose base is not an ancestor of the head; copy detection; rendering source excerpts in the Markdown (they are in the JSON); and any user interface beyond the command.
