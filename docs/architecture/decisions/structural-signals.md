# ADR: Structural Signals and Deterministic Candidates

**Decision:** Per-snapshot import relationships (direct import, test-to-source) extracted with the B1 parser and rules, stored as derived data, and combined with the M3 lexical signals under the full B6 category precedence. The result is the deterministic candidate list that later feeds RRF; it generates no Evidence.
**Context:** B1 (`experiments/structural/index.js`) extracted imports, resolved relative paths against the tracked files of one commit, and classified edges relative to the changed files; B5 unioned it with B2; B6 ranked the union (`experiments/ranking/index.js`). The research documents and code disagree in one place: the B1 README says it used the TypeScript compiler API, but the code uses `@babel/parser` with the `typescript` plugin. The TypeScript package here is 7.x, whose native compiler has no in-process `createSourceFile`, so the API the README describes is not available. Babel is the parser the research results actually came from, so production uses it.
**Alternatives:**
- *TypeScript compiler API:* unavailable at 7.x as above; pinning a second, older TypeScript only to parse would add a toolchain for no behavioral gain.
- *Tree-sitter or a regex scanner:* no evidence for either; they would change which texts parse.
- *tsconfig paths and other aliases, bare-module resolution:* not in B1 and not added.
- *Leaving `.js` specifiers unresolved, as B1 did:* rejected after measuring it. The WollyWay repositories use the Node ESM / TypeScript convention (`.ts` sources, `.js` in relative specifiers), so B1's rule left every backend import unresolved. See the resolution bullet.
**Chosen approach:**
- **Model** (migration 3, derived): `structural_parsed_content(content_sha256, dialect, status)` and `content_import(content_sha256, dialect, specifier)` hold content-level facts, shared by every snapshot and repository with that text. `snapshot_relationship(snapshot_id, source_artifact_id, target_artifact_id, kind)` holds resolved edges in one direction, source imports target, with composite foreign keys so both ends are versions in that snapshot; reverse lookups use `(snapshot_id, target_artifact_id)`, an index whose absence turns them into a scan of the snapshot's whole edge set. `kind` is `imports`, plus `test-to-source` as an additional row when the importing path is a test. `structurally_indexed_snapshot` marks completeness, including snapshots with no edges. `dialect` (`typescript` or `typescript-jsx`) is part of the content key because the same text parses differently with JSX enabled.
- **Extraction** (`src/analysis/import-extraction.ts`): every `ImportDeclaration` anywhere in the tree, i.e. default, named, namespace, side-effect and `import type` forms. Not extracted, as in B1: `export ... from`, `import x = require()`, `require()`, dynamic `import()`. A text the parser rejects yields no imports and is recorded as `syntax_error`. Only `.ts .tsx .js .jsx` paths are analysed (not `.mts .cts .mjs .cjs`).
- **Resolution** (`src/analysis/module-resolution.ts`): only specifiers starting with `.`; `posix.join(dirname(source), specifier)` plus the first existing of `''`, `.ts`, `.tsx`, `.js`, `.jsx`, `/index.ts`, `/index.js` among the Git paths of that same snapshot. Bare modules, aliases and unresolved paths create no edge. An import of the file itself is dropped. **`.js` extension (approved after the first benchmark):** only when every B1 candidate fails and the specifier ends in `.js`, the same path with `.js` replaced by `.ts`, then `.tsx`, is tried. An existing exact target always wins (an existing `foo.js` is never replaced by `foo.ts`), and no other extension is substituted (`.css`, `.mjs`, `.jsx`, `.json` and the like stay unresolved).
- **Test heuristic:** the importing path contains `.test.` or `.spec.`.
- **Lifecycle:** `indexSnapshotStructurally(db, snapshotId)` is explicit, idempotent and atomic, separate from ingestion and from `ready`. Retrieval throws `StructuralIndexNotBuiltError` rather than return partial results.
- **Candidates** (`retrieveCandidates`): the union of the lexical matches and the artifacts structurally related to the query's `changedPaths`. Signals are typed: `test-to-source` (a test importing a changed artifact), `incoming-import` (importing a changed artifact), `outgoing-import` (imported by a changed artifact). A test is one `test-to-source` signal, as in B1, not also an import signal. Candidates carry the lexical facts of M3, `lexicalCategory` (null when no term matched), the signals with the changed path each relates to, and per-kind counts.
- **Ranking** (`src/retrieval/deterministic-ranking.ts`), B6's precedence: `critical-structural` (incoming import or test) > `path-and-multi-content` > `high-content-density` > `weak-structural` (outgoing import) > `path-only` > `multiple-terms` > `single-term`; ties use the M3 lexical tie-breaks (distinct terms, path terms, shorter path, code-unit order). Structural-only candidates have no terms and fall to the path tie-breaks.
**Differences from B1/B5/B6:**
- *JSX.* B1 parsed everything without the JSX plugin, so a `.tsx`/`.jsx`/`.js` file containing JSX failed to parse and contributed no imports. Production enables JSX for those extensions. No edge touching a changed file differs on the benchmark histories, but the behavior is different.
- *Resolution universe.* B1 resolved against every tracked file; production resolves against the snapshot's ingested artifacts, so a target excluded by the file policy (for example a `.css` file) is unresolved.
- *`.js` specifiers* resolve to `.ts`/`.tsx` sources as described above; B1 left them unresolved, which is why it found no structural candidates in the four WollyWay backend cases.
- *Self-imports* are dropped (B1 would have recorded the file as its own dependency).
- *Ranking inputs.* Lexical inputs are M3's whole-token terms, not B2's substrings (see the lexical ADR), so ranks need not equal B6's.
**Benchmark** (`test/benchmark/deterministic-benchmark.test.ts`, base-commit snapshots): recall over the 7 positive cases Top-1 2/7, Top-3 3/7, Top-5 3/7, Top-10 4/7, Top-20 6/7 (lexical only: 3, 4, 4, 4, 6 of 7; B6: 3, 4, 4, 5, 7). Ranks TB-0001..0007: 7, 35, 1, 1, 2, 20, 11 (B6: 12, 1, 1, 1, 2, 8, 17). Every B1 edge is kept. The `.js` rule adds structural candidates in exactly three cases: TB-0001 19 (5 incoming, 14 outgoing), TB-0002 34 (incoming), TB-0006 11 (6 incoming, 5 outgoing); TB-0007 gains none because nothing imports its changed `.tsx` file statically. Each added edge was checked against an independent extraction as a genuine `.js`-to-`.ts`/`.tsx` substitution. TB-0003, TB-0004 and TB-0005 are unchanged (ranks 1, 1, 2; TB-0005 was 60 under lexical retrieval alone), and TB-0009's negative ranks 3, structurally flagged, as in B6. The documentation labels of the WollyWay cases fall because correctly found importers now rank above them: the structural categories outrank lexical ones by design, and the labels are documentation that no import relates to the change.
**Tradeoffs:**
- *Pros:* B1's relationships reproduced exactly where the benchmark exercises them; content parsed once; every edge is between artifacts of one snapshot; structural precedence is explicit and typed.
- *Cons:* imports are the only relationship, so transitive and co-change signals are absent, and aliases (tsconfig `paths`) stay unresolved. Documentation that the code does not import (the TB-0001, TB-0002, TB-0006 and TB-0007 labels) can only be reached lexically and now sits below the correctly found importers, which is the cost of precise structural recall that semantic retrieval and fusion are meant to address.
