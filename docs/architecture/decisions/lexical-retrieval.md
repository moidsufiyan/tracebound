# ADR: Production Lexical Retrieval

**Decision:** Snapshot-scoped lexical retrieval over Artifacts, using the B2 tokenizer behavior and the lexical categories of the B6 deterministic ranking, backed by a derived inverted index in SQLite. It is the deterministic input to the later hybrid/RRF layer; it generates no Evidence.
**Context:** B2 (`experiments/lexical`) searched with `git grep -i` and path substring matching; B6 (`experiments/ranking`) ranked B1 structural plus B2 lexical candidates by category. Production needs the same signals over ingested snapshots, reproducibly and without touching HEAD or the working tree.
**Alternatives:**
- *SQLite FTS5.* Verified available in the project's `node:sqlite` build (`ENABLE_FTS5`, virtual table created and queried). Not used: FTS5 reports which rows match an expression, not which query terms matched in each row, and B6 counts distinct matched terms (and path terms). Per-term matching would need one MATCH per term plus a rowid-to-content mapping table (`content` has a text primary key), all while ignoring FTS5's own tokenizer and BM25. A plain inverted table keyed by `(token, content_sha256)` gives exact per-term matches from a primary key and nothing else to maintain. FTS5 remains available if corpus size ever requires it.
- *BM25 / TF-IDF / embeddings:* not the established B6 behavior; excluded by scope.
- *Indexing during ingestion:* would couple a derived index to snapshot publication. Indexing is a separate explicit step instead.
**Chosen approach:**
- **Index** (migration 2, derived data, never part of what makes a snapshot `ready`): `content_token(token, content_sha256)` keyed by content, so shared content is tokenized once; `lexical_indexed_content` marks completed content (including content with no tokens); `artifact_path_token(artifact_id, token)`. `indexSnapshotLexically(db, snapshotId)` indexes whatever a ready snapshot references that is not yet indexed, in one transaction. It is idempotent and is also the backfill for snapshots ingested before the index existed. `searchLexical` throws `LexicalIndexNotBuiltError` for an incompletely indexed snapshot rather than returning partial results.
- **Scoping:** every search joins from the requested snapshot's `artifact_version` rows. Failed and unknown snapshots are rejected; there is no implicit "latest".
- **Candidates:** one per Artifact present in the snapshot that matched a path term or a content term, so a path-only match survives an empty content match. Artifacts sharing content are separate candidates. The result carries rank (1-based, directly usable as the rank in `1 / (60 + rank)`), artifact and version ids, path, kind, category, content/path match counts and matched terms.
- **Tokenizer** (`src/retrieval/tokenizer.ts`): lowercase; split camelCase (lower-to-upper boundary) and snake_case; every other non-letter/digit is a separator; queries drop B2's stop list (including `ts js md src index backend frontend docs test spec file ...`; `tsx` is not listed, as in B2) and tokens shorter than three characters. Explicit symbol names stay searchable even when short or a stop word (B2's TB-0003 `some` case, generalized). The index stores unfiltered tokens.
- **Ranking** (`src/retrieval/lexical-ranking.ts`): B6 categories `path-and-multi-content` (B6 tier 2), `high-content-density` (3), `path-only` (5), `multiple-terms` (6), `single-term` (7); then distinct matched terms, path terms, shorter path, path in code-unit order. B6 tiers 1 and 4 (incoming and outgoing structural dependencies) need structural analysis and are not part of `searchLexical`; the structural ADR adds them in `retrieveCandidates`.
**Differences from the B2/B6 research, and why:**
- *Whole tokens instead of substrings.* B2 matched `fix` inside `prefix`. Production matches whole tokens, so every production candidate is also a B2 candidate (asserted by the benchmark test) but not the reverse.
- *Compound identifiers also index their joined form* (`releaselocklua`), reproducing B2's whole-symbol query term under token matching.
- *All punctuation separates tokens* (B2 left some, such as `,`, attached). Required for token matching.
- *Locale-independent tie-break* (code units) instead of `localeCompare`.
- *File policy.* Only ingested artifacts are searchable; B2 searched every tracked file.
**Benchmark** (`test/benchmark`, needs `TRACEBOUND_WOLLYWAY_REPO` and `TRACEBOUND_HONO_REPO`; base-commit snapshots; changed files removed unless labelled, as in B2). Production lexical-only recall over the 7 positive cases: Top-1 3/7, Top-3 4/7, Top-5 4/7, Top-10 4/7, Top-20 6/7. Positive ranks: TB-0001 2, TB-0002 1, TB-0003 1, TB-0004 1, TB-0005 60, TB-0006 16, TB-0007 11. Candidates per case 154–364 (B2: 187–396). The TB-0009 negative ranks 5 in the top category, so lexical signals alone do not suppress it.
**Tradeoffs:**
- *Pros:* deterministic, exact snapshot isolation, per-term attribution, no new infrastructure, derived data that can be dropped and rebuilt.
- *Cons:* cost per search grows with the snapshot's artifact count times the number of terms (one primary-key probe each); whole-token matching loses substring-only recall (TB-0005 falls from rank 3 to 60 because B2's rank leaned on `fix` matching `prefix`); candidate volume stays in the hundreds; callers must run `indexSnapshotLexically` after ingestion.
