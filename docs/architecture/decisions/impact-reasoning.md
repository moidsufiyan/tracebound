# ADR: Impact Reasoning

**Decision:** An optional reasoning step turns an M7 evidence package into a structured, cautious assessment per candidate. A model reads the evidence as data and answers in a fixed schema; a deterministic validator checks the answer's structure and references; the caller gets a report that cites evidence ids or gets an error. No report is produced from a failed or invalid answer.
**Context:** The [evidence ADR](evidence-model.md) places the LLM after retrieval and evidence, and M7 provides stable, verified evidence per candidate. What is still missing is a way to say what the evidence supports without turning a rank, an RRF agreement, an import or a similarity score into a claim of impact. The benchmark shows why: the TB-0009 helper imports the changed utility, shares its vocabulary and is ranked third by both modalities, yet that change is internal.
**Chosen approach:**
- **Input** (`src/reasoning/provider.ts`): `ReasoningInput` is the snapshot id and commit, the change description and changed paths, and the candidates of the evidence package with their M7 evidence items and ids. It is built from the supplied package; nothing is retrieved, embedded or constructed again, and no raw repository file is added. The input is serialized as JSON (`serializeReasoningInput`), separately from fixed system instructions (`IMPACT_REASONING_INSTRUCTIONS`), which are never composed from the change or the repository.
- **Classification** (`src/reasoning/impact-report.ts`): `likely_affected` (the evidence supports a specific relationship to the behavior the change describes; a structural link alone is not enough if that behavior is not established), `potentially_affected` (plausible, not established), `no_impact_indicated` (the evidence affirmatively supports no impact; the absence of a signal is not that), `insufficient_evidence`. There is no confidence number.
- **Output:** per candidate `{ artifactId, versionId, path, classification, findings: [{ statement, evidenceIds }] }`; the report adds the snapshot id and the reasoning model id and keeps the candidates in the order supplied. Each finding carries its own citations, so it is clear which evidence supports which statement.
- **Provider** (`ReasoningProvider`): `modelId`, `maxInputChars` and `reason(request)`, which returns an `unknown` payload. The one adapter, `createOllamaReasoningProvider`, is configured with the model name and the input budget; neither has a default. It checks that the server has the model, puts the weights' digest in the model id, asks for JSON constrained to the output schema with temperature 0 and a fixed seed, applies a timeout, and fails clearly for an unreachable server, a missing or failing model, a cut-off answer, text that is not JSON, or a timeout. It holds no credentials; a future adapter that needs one would take it from configuration and must not log it.
- **Validation** (`validateImpactOutput`): required fields and types, no unexpected fields, the snapshot, exactly the candidates supplied by artifact, version and path (each once; missing, duplicate and unexpected ones are errors), a permitted classification, every non-abstaining assessment having at least one finding, every finding having a non-empty statement and at least one evidence id, every id being evidence of that same candidate and not repeated, and bounded sizes (1,000 characters per statement, 10 findings per candidate, 20 ids per finding, 100,000 characters of statements per request). Nothing is repaired or dropped.
- **Budget:** `planReasoningBatches` measures a request as the instructions plus the serialized input and splits the candidates, in order and at candidate boundaries, into the fewest consecutive requests that fit `maxInputChars`. A candidate whose complete evidence cannot fit alone raises `ReasoningInputTooLargeError` naming it, before any request is sent; evidence is never shortened to fit. Requests are sent one at a time, without retries. Any provider error or invalid answer fails the whole analysis (`request n of m: …`), and no partial report is returned.
**Security:** the change description and the source excerpts are untrusted. They are serialized as JSON string values in a separate message from the instructions, and the instructions tell the model to treat them as data, to use no tools and to assess candidates independently. Tests check that the serialization is safe and that an answer following an injection is rejected when it is malformed; they do not show that a model resists injection. The reasoning layer cannot search, run commands or reach the network. It logs no prompts, excerpts or responses (provider error messages contain a status and at most 200 characters of the server's own error text, never the model's answer).
**What validation does not establish:** that a statement is true or follows from the evidence it cites, that a classification is correct, or that two candidates were assessed independently. A report is a model's reading of the evidence with its sources attached, to be reviewed, not a verdict.
**Evaluation limits:** the Phase 1 case labels are retrieval relevance labels (`direct-impact`, `investigation-worthy`, `contextual-historical`, `not-relevant`, `uncertain`), not impact classifications, and a candidate being the labelled retrieval target does not say how the change affects it. Nothing in the repository therefore establishes what the right classification of any candidate is, and no accuracy is claimed. The only reference is the negative TB-0009 candidate, labelled `not-relevant`: a `likely_affected` assessment of it must not rest on retrieval agreement alone, which the opt-in benchmark checks by the evidence it cites. Impact-level human annotations would be needed to score classifications.
**Opt-in run with a real model** (`test/benchmark/reasoning-benchmark.test.ts`; `qwen2.5-coder:7b` through local Ollama, 14,000-character budget, 8,192-token context, five candidates per case; four cases run: TB-0002, TB-0006, TB-0007, TB-0009; not the other five). (1) Validity: three reports were valid; for TB-0006 the validator rejected the model's answer because a finding cited another candidate's evidence id, so that analysis failed with no partial report. (2) Classifications in the valid reports: 4 `likely_affected`, 6 `potentially_affected`, 5 `no_impact_indicated`, no `insufficient_evidence`. (3) Accuracy: not measured, for the reason above. (4) For review: all five `no_impact_indicated` assessments (TB-0007) cite only lexical and semantic evidence, which is hard to square with the definition that absence of a signal is not affirmative evidence; the TB-0009 negative, the helper that imports the changed utility, was classified `likely_affected` with a finding that it imports the changed file and uses its `abort` method, citing structural, lexical and semantic evidence. The benchmark's own check (a `likely_affected` assessment must not cite only fusion evidence) passed, but the label for that candidate is `not-relevant`. So a 7B local model followed the schema and the citation rules most of the time, did not reliably follow the caution rules, and validation could not catch that. Using a stronger model, or a person reviewing the flagged claims, is outside what this milestone establishes.
**Tradeoffs:**
- *Pros:* every statement is tied to evidence of its own candidate; failures are explicit; the budget never silently drops evidence; the model is replaceable behind a three-member interface; no persistence or infrastructure.
- *Cons:* the quality of the reasoning is that of the chosen model, which the repository cannot verify; a small input budget forces more requests and each request sees fewer candidates (which also keeps candidates independent); a character budget is only a proxy for the model's token context.
