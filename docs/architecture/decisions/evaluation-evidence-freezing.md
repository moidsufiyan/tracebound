# ADR: Evaluation Evidence Freezing (M9)

**Decision:** The annotation pilot's inputs are frozen from one production retrieval run per case into canonical, digest-identified artifacts and a frozen SQLite file, checked by an offline verifier. The tooling lives in `src/evaluation/m9/` and reads M1–M8 without changing them.
**Context:** Human annotation needs evidence that cannot drift: the same candidates, the same evidence ids and the same source text for every annotator, with a way to show afterwards that nothing changed. Evidence is deliberately never stored (see [evidence construction](evidence-construction.md)) and ids are SQLite row ids, so a stable record has to be produced and kept outside the retrieval path. The selection itself is a protocol decision, recorded in [`docs/evaluation/m9/protocol-amendment-1.3.0.md`](../../evaluation/m9/protocol-amendment-1.3.0.md).
**Chosen approach:**
- **Frozen database** (`freeze-database.ts`): a copy made with SQLite's backup API from a read-only connection, folded into one file (checkpointed, rollback-journal mode, no sidecars), with `integrity_check`, `foreign_key_check`, size, SHA-256, schema version and per-table row digests recorded. The source's bytes are hashed before and after. Retrieval for the release runs against the frozen file opened read-only.
- **One run, three records** (`artifacts.ts`): the production `searchHybridDetailed` result feeds `constructEvidence` (normal limit) and the ranking record; nothing is retrieved or embedded twice. The archival package carries the evidence objects exactly; the ranking record carries the whole fused ranking with eligible ranks; the review packet is derived from the package.
- **Canonical form:** RFC 8785 (JCS) through `canonicalize` 5.1.0; digest = SHA-256 of the canonical bytes; the digest of an artifact is never inside it. Values JSON cannot represent are rejected, timestamps are UTC with milliseconds, paths are validated as portable POSIX paths and never rewritten.
- **Identity is database-scoped:** artifact and version ids, and the evidence ids built from them, are rows of the release database; every artifact says so.
- **Blinding:** a review packet has the change, three candidates with hash-checked source and their own evidence, and one blank annotation record per candidate (schema 1.1.0, `annotation.ts`). It never has reasoning output, reasoning-model identity, labels or other candidates; the verifier checks this.
- **Release gate** (`gate.ts`): the manifest records `distribution.status`, `RELEASED` only when the verifier passes the manifest as written. `reconcilePackets` can rebuild just the packets of an existing release without touching the database or evidence packages.
- **Offline verifier** (`verify.ts`): reads only the release directory, opens the database read-only, runs no model, retrieval or Git command.
**Not established:** authenticity (a hash proves integrity, not origin); that a candidate is impacted; any classification accuracy.  The v1.2.0 protocol text is not in the repository; the annotation contract follows the schema the evaluation owner supplied.
**Tradeoffs:**
- *Pros:* annotators and later reviewers can prove they used identical inputs; the run can be audited without Ollama; M1–M8 are untouched.
- *Cons:* the release holds a full database copy and is large; ids do not transfer to another database; a new export is a new run with new timestamps, so its package digests differ even when its rankings match.
