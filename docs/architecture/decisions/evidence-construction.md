# ADR: Evidence Construction

**Decision:** Evidence is built on demand, per request, from the retrieval run that produced a hybrid ranking and from the immutable data of the snapshot it ran against. It is a set of typed facts about why a candidate was retrieved. It is not stored, and it never concludes that a candidate is impacted.
**Context:** The [evidence ADR](evidence-model.md) makes Evidence a first-class object between retrieval and reasoning. Retrieval now yields everything evidence needs (M3 lexical facts, M4 structural signals, M5 semantic scores, M6 fusion), but `searchHybrid` returned only the fused list, which drops the modality-specific facts. Recovering them by searching again would repeat the retrieval and re-embed the query.
**Chosen approach:**
- **One run.** `searchHybridDetailed` (`src/retrieval/hybrid-search.ts`) is the single execution path; `searchHybrid` is `(await searchHybridDetailed(...)).fused`, so its results and return type are unchanged. The detailed result keeps the snapshot id, the query, the RRF constant used, the model id, and the complete deterministic, semantic and fused rankings. `constructEvidence(db, snapshotId, provider, result, { limit? })` consumes it. It never searches, embeds or calls the provider's `embed`; the provider is passed only so the semantic index can be checked for the model.
- **Evidence types** (`src/retrieval/evidence.ts`, a discriminated union on `type`):
  - *structural:* a verified file-level relationship between the candidate and a changed file: the signal (`test-to-source`, `incoming-import`, `outgoing-import`), the relationship row that was found in the snapshot, source and target versions (source imports target), which of them is the candidate, the changed path, and the import declarations in the importing file that resolve to the target, each with its specifier, 1-based line range and a source excerpt. `declarations` is null when they cannot be located.
  - *lexical:* the matched terms, lexical category and the content and path counts, which are numbers of distinct query terms, not occurrences. No locations or snippets.
  - *semantic:* model id, cosine similarity, winning chunk index, chunk count, the SHA-256 of the exact text embedded for that chunk, and the chunk's source text without the embedding framing (null when it cannot be reconstructed).
  - *fusion:* fused rank, RRF score, the K the run used, and each modality's rank and contribution `1/(K + rank)`, which must add up to the score within 1e-12.
- **Order and ids.** Candidates stay in fused-rank order with their original ranks. Evidence within a candidate is structural, lexical, semantic, fusion; structural items are ordered by signal kind and changed path. Ids are composed from identity fields (`structural:<signal>:<source version>><target version>`, `lexical:<version>`, `semantic:<version>:<model>:<chunk>`, `fusion:<version>:k<K>`), so they are stable and never random; an identical item listed twice is kept once and distinct relationships are never merged. The bundle is deeply frozen.
- **Selection.** Candidates whose path equals a changed path (exact comparison) are removed first, then the first `limit` (default 20) are described. Nothing is reranked and the hybrid result is not modified. A changed path the snapshot does not contain (a file the change adds) is kept in `changed` with null ids; no artifact is invented.
- **Verification.** Before anything is built: the snapshot must exist, be ready, and have the lexical, structural and the model's semantic index; the run must be for that snapshot and model; every selected candidate must be that version, artifact, path and kind in the snapshot and must agree with what the run's own deterministic and semantic rankings say about it; every structural signal must match a `snapshot_relationship` row with the right kind and endpoints; the fused score must equal the sum of its contributions. A failure throws (`InconsistentCandidateError` for an inconsistent run, the existing snapshot and index errors otherwise); no candidate is dropped and no fact is invented.
- **Source reconstruction.** *Imports:* the importing file's immutable content is parsed again with the same Babel configuration as indexing (`locateImportDeclarations`, which finds the same declarations `extractImports` does but with positions), and the declarations whose specifier resolves, by the indexing's own resolution rules and the snapshot's paths, to the target are reported. Excerpts are the declaration's exact text, at most 500 characters. *Chunks:* the content is chunked again with the deterministic chunker, at the index's limit and then at the halved limits that indexing falls back to, and a chunk counts only if its input hashes to the stored hash; the text shown is that input minus its `search_document: File: ...` framing (`sourceTextOfInput`), at most 1,000 characters. A longer excerpt carries `truncated: true` and the full length.
**Limitations:**
- Structural evidence is about files: it establishes that one file imports another, not which symbols are used. Only B1's relationships exist, so there is no co-change or transitive evidence. Line numbers refer to the normalized content (LF endings), which differs from the raw blob only for files that used a bare CR.
- Only the winning semantic chunk is described. A line-split chunk ends each line with a newline, as B7.1 did, so its text can end with one more newline than the file does. Lexical evidence has no locations.
- Evidence cannot be recomputed for a run whose rankings were not kept, because the rankings are the evidence's input.
**Why a ranking is not proof of impact:** a rank says a candidate looks like the query, or is connected to a changed file, more than other artifacts do. B7.1 and the benchmark show the gap: the TB-0009 helper imports the changed utility, shares its vocabulary, and both modalities rank it third, yet that change is internal and the helper needs no investigation. Evidence records why a file was surfaced so that a person, or a later reasoning step bounded by these facts, can judge it. It carries no impact label, confidence or explanation.
**Why nothing is stored:** every item is a function of immutable inputs, the snapshot's content and relationships and the run's rankings, so it can be rebuilt exactly and cannot go stale. A table would add a second source of truth that has to be kept in step with the indexes, and the run-specific parts (the query, the scores) belong to the request rather than the snapshot.
**Benchmark check** (`test/benchmark/evidence-benchmark.test.ts`, real repositories and Ollama, top 50 candidates of each of the nine cases): every run verified; the import declaration of all 68 structural facts was located; the source text of all 450 semantic chunks was reconstructed with no framing; all fusion contributions add up. TB-0009: the negative is found by both modalities (3 and 3, fused 3) with one incoming-import fact, `src/helper/streaming/stream.ts` importing `src/utils/stream.ts` on line 2, and the evidence says nothing more.
