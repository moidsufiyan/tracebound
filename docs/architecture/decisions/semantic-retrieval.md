# ADR: Semantic Retrieval

**Decision:** An independent semantic candidate pipeline: B7.1's embedding inputs, embedded by a local Ollama server with `nomic-embed-text:v1.5`, stored per model in SQLite, searched by exact cosine similarity against an explicitly supplied ready snapshot. It produces ranked candidates for the later RRF step and does no fusion, reranking, query rewriting or evidence generation.
**Context:** B7/B7.1 (`experiments/semantic/index.js`, `docs/semantic/`) embedded `search_document: File: <path>\n\n<text>` for each file and ranked artifacts by their best chunk against `search_query: Change Description: ...`. Reading the code instead of the summaries showed three things the summaries do not say:
- B7.1 chunks only files longer than 28,672 characters, with one 25,000-character limit; the Markdown splitter breaks at any heading level (`^#+ `, not only `^# `); the TS/JS splitter's regex contains a capturing group, so `split` inserted the matched keyword (`"export "`, `"function "`, `"class "`) as a stray extra part.
- The served model's context is 2,048 tokens, not 8,192, and Ollama truncates longer inputs without any error. Probed against B7.1's own cache: for a 10,249-character file the cached vector and a fresh embedding of the first 2,048 tokens have cosine 1.00000, while `truncate: false` is rejected. Every B7.1 input over about 5,000 characters was therefore embedded as its first 2,048 tokens, whole file or "chunk" alike, so B7.1's chunking did not repair truncation.
- Embeddings were cached by text only, with no model or dimension recorded.
**Alternatives:**
- *Reproduce B7.1 exactly, including silent truncation:* rejected; an embedding that covers only part of its input without saying so is not a defensible production representation.
- *Native vector search (sqlite-vec, pgvector, an external store):* out of scope and unnecessary: a snapshot has a few thousand chunks, and exact cosine over them is a loop.
- *Key embeddings by (content, model, chunk index):* wrong, because the input text includes the file path.
**Chosen approach:**
- **Provider** (`src/semantic/provider.ts`, `ollama-provider.ts`): `{ modelId, dimensions, maxInputChars, embed(texts) }`. The Ollama implementation reads the installed digest and embedding length from `/api/tags`, so the model id is `ollama:nomic-embed-text:v1.5@<digest prefix>` and a re-pulled build gets a new id. It sends `truncate: false`, maps a context-length rejection to `EmbeddingInputTooLongError`, and validates every response (count, per-vector length equal to the declared dimensions, finite values, no zero vector); nothing is truncated, padded or coerced. `maxInputChars` is 3,500: the shortest text seen was 2.4 characters per token (about 4,900 characters in 2,048 tokens), leaving margin.
- **Chunking** (`chunking.ts`): the B7.1 format unchanged for files that fit (`search_document: File: <path>\n\n<text>`) and `... File: <path> (Chunk n)` for pieces; Markdown at headings, TS/JS at line-leading `export`/`function`/`class`, anything else by lines, an over-large part by lines, a line longer than the budget by characters (never inside a surrogate pair). The limit is the provider's `maxInputChars` rather than B7.1's two constants.
- **Identity and storage** (migration 4, derived): `semantic_embedding(model_id, input_hash, dimensions, vector)` is unique on `(model_id, input_hash)`, where `input_hash` is the SHA-256 of the exact text sent, which includes the path; the vector is little-endian float32. `semantic_chunk(model_id, snapshot_id, artifact_id, chunk_index, input_hash)` records a snapshot's chunks per model and is tied by composite foreign keys to an artifact version of that snapshot and to an embedding of the same model. `semantic_indexed_snapshot(model_id, snapshot_id, dimensions, max_input_chars)` marks completion. Artifact, ArtifactVersion, Content and `ready` are unchanged.
- **Lifecycle:** `indexSnapshotSemantically(db, snapshotId, provider)` plans chunks, finds stored embeddings for the model, sends only the missing inputs in batches of 16, stores each batch in its own short transaction (provider calls never run inside one), and writes the chunks and the marker in one final transaction. It is idempotent per (snapshot, model); a failure leaves no marker, and the retry reuses what was stored. An input the provider still rejects as too long is never truncated: its artifact is chunked again at half the limit, repeatedly, down to 400 characters, then the indexing fails with the path. This is needed in practice: a JSON file of encoded keys in the Hono benchmark repository exceeds the context at 3,500 characters.
- **Search:** `searchSemantic(db, snapshotId, provider, { description, changedPaths })` requires a ready snapshot indexed for the provider's model (`SemanticIndexNotBuiltError`; `SemanticIndexIncompatibleError` for other stored dimensions or limits), embeds the B7 query, scores every chunk of that snapshot and model by exact cosine similarity, keeps each artifact's best chunk, and orders by similarity, then path (code units), then artifact id. Candidates are drawn from the snapshot's own chunk rows joined to its versions, so a shared embedding never adds an artifact the snapshot lacks, and other models' vectors are never read.
- **Candidate:** `{ rank, artifactId, versionId, path, kind, similarityScore, bestChunkIndex }`; `rank` is 1-based and directly usable in `1 / (60 + rank)`.
**Differences from B7.1, and why:**
- *Input size.* The 3,500-character limit and the re-chunking on rejection replace B7.1's constants, because the model cannot accept B7.1's inputs without truncating. About a third of the artifacts in the benchmark snapshots are longer than that and are now covered in full by several chunks instead of by their first 2,048 tokens.
- *TS/JS splitter* without the stray keyword parts; *line-based splits* are otherwise B7.1's, including its trailing newline per line.
- *Artifact universe:* the ingested artifacts (file policy) instead of every non-binary tracked file; content is normalized (LF, no BOM).
**Benchmark** (`test/benchmark/semantic-benchmark.test.ts`, run against a real Ollama server; base-commit snapshots; B7.1 protocol, which ranks every artifact including the changed files):
- Every one of the 2,457 artifact scores that rest on a whole-file input matches B7.1 to four decimals, and all of those inputs are found in B7.1's embedding cache: the formatting, normalization and search arithmetic agree with the research wherever the input is the same.
- Recall over the 7 positive cases: Top-1 0/7, Top-3 4/7, Top-5 4/7, Top-10 4/7, Top-20 7/7 (B7.1: 0, 3, 6, 7, 7). Ranks TB-0001..0007: 13, 2, 2, 2, 3, 18, 13 (B7.1: 4, 2, 5, 2, 3, 9, 5). The rank differences come only from artifacts that are now chunked: the labelled documents score exactly as in B7.1 (for example 0.7012, 0.7689, 0.6868 and 0.6981), while other long files now match the query through the chunk that is actually about it and rise above them. Every labelled candidate is within the top 20.
- Against the deterministic pipeline (changed files removed, as that was evaluated): semantic ranks TB-0001, 0002, 0003, 0004, 0005, 0006, 0007 are 12, 2, 1, 1, 2, 16, 12 and deterministic ranks are 7, 35, 1, 1, 2, 20, 11. Semantic retrieval recovers TB-0002 (35 to 2), improves TB-0006 slightly, and does not beat the lexical signal on TB-0001 and TB-0007; where deterministic retrieval is already first (TB-0003, TB-0004) the two agree.
- TB-0009's negative ranks 3 (similarity 0.7125, as in B7.1): the semantic false positive remains. Candidate volume is every artifact of the snapshot (317 to 541).
**Tradeoffs:**
- *Pros:* embeddings are shared across snapshots and repositories and never mixed across models; exact and deterministic; no native extension; a stored vector can be checked against its model, dimensions and exact input.
- *Cons:* no tokenizer, so the character limit is a margin and the fallback re-embeds an artifact smaller when the model refuses an input (the pieces of that artifact then depend on the server's behavior, which is deterministic but not derivable from the text alone); the first indexing of a snapshot costs one provider call per new chunk (about 15 per second on the development GPU, 2,586 distinct inputs for the nine benchmark snapshots); every search loads and compares all of a snapshot's vectors; retrieval quality is that of a 137M-parameter general model, with top-1 precision and neighborhood clustering as B7.1 found.
